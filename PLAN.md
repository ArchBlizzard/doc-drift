# DocDrift — 44-Hour Build Plan

A dataset-audit agent that verifies every claim in a data card against the actual data by writing, **mutation-testing**, and executing its own checks.

> Picked by a 3-judge rubric panel from 10 candidate ideas (avg expected score 80.3/100).
> Runners-up kept in reserve: **DeFlake** (flaky-test fixer with a bug-twin verification harness, 79.3) and **RefGuard** (citation-forensics agent with registry-backed evidence, 79.0).

---

## 1. Pitch

Data engineers and ML practitioners who inherit datasets — a Kaggle download, a UCI classic, an internal handoff — routinely trust a README that says "no nulls in `patient_id`, dates cover 2015–2023, 12 categories" while the parquet file quietly disagrees; today the check is either skipped or a half-hour of ad-hoc pandas per dataset. A single LLM prompt visibly cannot do this job: a 500k-row file does not fit in context, so a one-shot answer over the doc plus `head(50)` is guessing — it misses violations hiding in rare slices past row 500 and hallucinates confirmations of statistics it never computed. DocDrift is a Claude Agent SDK pipeline that extracts typed claims from the data card, synthesizes one pandas check per claim, **mutation-tests each check against a deliberately-violating fixture before trusting it** (killing the "green because the check is vacuous" failure mode), executes checks against the full file on disk (data never enters model context — exactly why the agent beats the prompt structurally), and emits an audit report a human would sign, with computed-vs-claimed values and offending rows. The eval cases, gold labels, and scorer are offline and fully deterministic — judges regenerate them bit-for-bit and reproduce the scored comparison end-to-end; model outputs vary slightly run to run (disclosed), so the submitted runs' complete outputs are committed.

## 3. Agent Architecture

**Orchestration mechanism:** plain Python **async pipeline** in `orchestrator.py` (anyio). Each stage is a single-purpose, **no-tools** Agent SDK query with a stage-specific system prompt and pydantic-validated JSON output (`llm.call_json`, ≤2 retries). The model is granted ZERO tools: profile, executor, and mutant fixtures are ordinary Python invoked by the orchestrator, with results flowing into the next prompt (research R9 — simplification settled during T019). Per-claim work fans out under `anyio.Semaphore(4)`. Deliberate choice to call out in the README: the orchestrator is deterministic Python and only *judgment* steps are LLM calls.

| Stage | Exact job | Capability used | Why it earns rubric points |
|---|---|---|---|
| **1. Claim Extractor** (Sonnet) | Reads `datacard.md`, emits typed claims JSON: `{id, type ∈ {schema, row_count, range, null_rate, category_set, aggregate_stat, temporal_coverage, prose_unverifiable}, quoted_span, params}`. Must quote the exact card substring per claim. Prose claims (provenance, collection method) are marked `unverifiable` — calibrated abstention is scored. | **Context engineering** — sees only the card + a `profile.py` snapshot (dtypes, head(20)); never raw data. | Shows purposeful context: extraction quality is isolated from data size, and quoted spans make scoring deterministic (see §5). |
| **2. Check Synthesizer** (Sonnet; Haiku as costed ablation) | Per claim, writes one self-contained `def check(df) -> {passed, computed, evidence_rows}` pandas function as a source string. System prompt includes current `lessons.md`. | **Tools + memory** — output is executable code, not an opinion; lessons.md injects accumulated pitfalls (dtype coercion, NaN semantics, tz-naive dates). | Code-as-verdict is the structural beat over the baseline; the memory file measurably reduces retries across cases (reported as retries-per-claim, case 1 vs case 12). |
| **3. Mutation Verifier** (Python + Sonnet on failure) | Before any check is trusted: `mutants.py` builds a ~20-row fixture that *satisfies* the claim and a mutated twin that *violates* it (null injected, category added, range breached, count off-by-one…). The check must pass the clean fixture and **fail the mutant**. A check that passes its mutant is vacuous → sent back to the synthesizer with the mutant diff; two strikes → claim marked `unverifiable(check_failed)` rather than trusted. | **Verification (the load-bearing trick)** — mutation-testing the agent's own verifiers. | This is verification *of the verifier*, with a before/after F1 in the changelog — the most direct answer to "purposeful verification" in the rubric. |
| **4. Sandboxed Executor** (custom tool, no LLM) | Runs the validated check against the **full** dataset in a `subprocess` (fresh interpreter, temp cwd, 60s timeout, output capped at 4KB, no network required by design). Returns `{passed, computed, evidence_rows(≤5)}` to the orchestrator; only the *summary* re-enters model context. | **Tools + context discipline** — the full data is touched exactly once, on disk, outside context. | Makes the baseline gap structural, not prompt-luck: the agent computes what the baseline can only guess. |
| **5. Run Ledger** | Append-only JSON per run: claim → check source → mutant result → verdict → computed evidence → timing/cost. Re-runs skip settled claims (hash of claim + data and card fingerprints). Doubles as the published trajectory. | **Memory + reproducibility** | One artifact serves three deliverables: trajectory, evidence trail, re-run cache. |
| **6. Reporter** (Sonnet) | Ledger → `audit.md`: per-claim verdict table (claimed vs computed), offending row examples, abstentions with reasons, one-paragraph executive summary. | **End-to-end quality** | The output a data engineer would actually paste into a handoff thread — targets the 20-pt "would sign their name to it" row. |

## 4. Baseline

`run_baseline.py case_XX`: **one direct Claude call** (same model, Sonnet) given the full data card, the column dtypes, and the first 50 rows as CSV text, asked for the identical per-claim output format (quoted span + verdict ∈ {holds, violated, unverifiable}). Same CLI shape, same output schema, same scorer. Implemented as a single no-tools Agent SDK query (`allowed_tools=[]`, `permission_mode="dontAsk"`) so it runs on the exact same auth path as the agent — no separate `anthropic` SDK or API key needed.

Why judges will consider it fair:

- It is the *honest* version of "just paste it into Claude" — what a practitioner actually does today, with the same model and the same information a human skimmer uses.
- **Baseline-plus preempts the strawman objection:** a second variant additionally receives `df.describe(include='all')` and per-column `value_counts().head(10)` — the best single-prompt version that still fits context. Both baselines are scored and published; the agent must beat both.
- Identical claim inventory treatment: both systems extract their own claims, both are scored against the same gold list by the same alignment rule, and an unmatched gold claim counts as a miss for either system.
- Both run offline against local files with a pinned model alias, so judges reproduce both sides with one command each. (Claude Code auth doesn't expose `temperature`, so runs aren't bit-identical — disclosed in README; the complete per-claim outputs for the submitted runs are committed in `results/`, and the scorer itself is fully deterministic.)

## 5. Eval Harness

**Primary metric:** macro-F1 over the three verdict classes {claim-holds, claim-violated, unverifiable}, computed per gold claim across all cases (~70 gold claims over 12 cases). Secondary: violation recall (the metric users feel), false-alarm rate, cost and wall-clock per case.

**Alignment (defusing the judges' main worry):** gold claims are *defined as character spans* in each data card (the corruption generator knows exactly which sentence it wrote or perturbed). Both systems must output the exact quoted substring for every claim; alignment is **span-overlap ≥ 0.5 IoU** — deterministic, auditable, no mushy fuzzy matching in the primary path. `rapidfuzz` token-set ratio ≥ 85 is a *fallback only* (used when a system paraphrases), and every fallback match is flagged in the published results so a skeptical judge can inspect all of them. Cards stay natural README prose — no numbered-statement lab conditioning.

**Cases (12, from 6 datasets, ground truth by construction):**

- **Committed directly in `data_src/`** (small, permissive licenses, no download): UCI Adult (census income, CC BY 4.0, ~48k rows), Palmer Penguins (CC0), UCI Wine Quality (red), UCI Online Retail II 40k-row sample, NYC Yellow Taxi Jan-2023 50k-row parquet sample (public domain), NOAA GSOD 2023 sample for 10 stations. Provenance + license per file in `data_src/README.md`, integrity via `SHA256SUMS`. **No network needed, ever** — this kills clean-clone friction for 5 of 6 sources.
- For each dataset, author one *accurate* data card (realistic prose: overview, schema table, coverage notes, caveats). Then `make_cases.py` applies a **seeded corruption spec** per case: 3–6 discrepancies drawn from 8 operators in `corruptions.py` (inject nulls, add/rename a category, shift a numeric range, drop/duplicate rows vs stated count, stale the date coverage, perturb a claimed mean/percentage, add a phantom column to the card, coarsen "roughly X%" language). Each operator edits **either the card or the data**, and emits the gold label + span automatically → `eval/gold/case_XX_gold.json`. Cases 01–06 are one draw per dataset; cases 07–11 are second corruption draws over five of the six datasets; case_12 is the synthetic hard case — 12 total. Every case also keeps 2–3 *true* claims and 1–2 *unverifiable* prose claims so "holds" and abstention are genuinely tested.
- **The hard case (`case_12`):** fully synthetic 1,000,000-row transactions parquet generated deterministically in-code (`numpy` PCG64, seed 20260829 — no download, ~25MB, generated by `make data` in <1 min). Its only violations: a rare status category `REFUND_X` appearing 173 times entirely after row ~810,000, and the card's "roughly 10% of `coupon_id` values are missing" when the truth is 14.2%. Head-of-file sampling provably fails the first; threshold judgment on fuzzy language tests the second.

**Scoring script (`eval/score.py`):** loads gold + a system's output JSON → span-align → confusion matrix → macro-F1, per-class P/R, per-case table. `eval/run_all.py` runs baseline, baseline-plus, and agent on all 12 cases and writes `results/results.md`:

```
| case | system | claims | holds P/R | violated P/R | unverif P/R | macro-F1 | violations caught | tokens | time |
```

plus a full per-claim appendix (`results/per_claim.csv`: case, claim span, gold, baseline, baseline_plus, agent verdicts, computed value). Complete tables for **all three systems** are committed, per the brief and Constitution VI.

## 6. Planned Improvement Changelog (CHANGELOG.md skeleton)

1. **v0 — Harness + baselines.** Eval cases, gold generation, scorer, and both baselines scored on cases 01–06. *Failure observed:* baselines confidently "verify" statistics they never computed and miss everything beyond the head sample. *Evidence:* `results/v0.md` (expect macro-F1 ~0.45–0.55 for both baselines).
2. **v1 — Split pipeline + full-data execution.** Dedicated extractor and per-claim synthesizer; every verdict must cite an executor result or abstain. *Fixes:* hallucinated confirmations. *Evidence:* violated-class recall jump, case_12 rare-category catch appears; per-claim diff v0→v1.
3. **v2 — Mutation-testing the checks (the standout).** Mutant fixtures gate every check. *Fixes:* vacuous-green checks — measure and publish the first-draft vacuous rate (hypothesis ~15–25%). *Evidence:* count of checks rejected by mutants + macro-F1 before/after + two concrete vacuous-check exhibits (e.g., a range check that compared `str` to `int` and always passed).
4. **v3 — lessons.md memory + abstention calibration.** Recurring synthesis pitfalls appended after each eval iteration and injected into the synthesizer; explicit abstention rules for fuzzy-language claims ("roughly X%" → tolerance band). *Fixes:* repeated dtype/NaN bugs and over-confident verdicts on prose. *Evidence:* retries-per-claim trend across cases; unverifiable-class F1 before/after.
5. **REMOVED — stratified-sample context stuffing.** Experiment: feed the baseline-plus three stratified 2,000-row samples in context instead of executing code (the "maybe we don't need code" test). *Result to record:* still misses the row-810k category (sampling probability of the 173/1M slice), 8–10x token cost, no F1 gain over baseline-plus → removed, kept in changelog with its numbers as required. (If the Haiku-synthesizer ablation loses F1, it is written up the same way; if it holds F1, it ships as the cost-optimized default — either outcome is a changelog entry with evidence.)

## 7. Tech Stack

- **Python 3.12** (single `pyproject.toml`, `uv` lockfile committed; pip fallback documented).
- **claude-agent-sdk** (Python, latest — pin exact version in lockfile at build time) for agent AND baseline. **Auth: no API credits required** — the SDK automatically reuses the local Claude Code subscription login when `ANTHROPIC_API_KEY` is unset; `claude setup-token` mints a long-lived `CLAUDE_CODE_OAUTH_TOKEN` as a portable alternative. Judges run the identical code with either their own API key or their own subscription login — no code branch.
- **pandas 2.2.x**, **pyarrow ≥ 17** (parquet), **numpy** (seeded case generation), **pydantic 2.x** (schemas), **rapidfuzz** (fallback alignment only), **rich** (live terminal trajectory — this is the video's visual), **pytest** (harness self-tests: corruption operators round-trip, scorer on hand-labeled fixtures).
- **Models:** alias `sonnet` (resolves to Sonnet 5) for extractor/synthesizer/reporter and the baselines; alias `haiku` (Haiku 4.5) for the synthesizer ablation — set via `ClaudeAgentOptions(model=...)`, pinned in one `config.py`. The resolved model ID from each run's response metadata is written into the ledger and REPRODUCE.md.
- **Sandbox note (Windows-honest):** executor = fresh `subprocess` python, temp cwd, 60s timeout, capped stdout; no `resource` module on Windows, so the cap is timeout + output size, disclosed in README. Nothing needs network at runtime.
- **Approximate cost:** **$0 in API credits** — all calls run on the builder's Claude subscription and count against its usage window, not a billed key. Volume is modest (≈ 5–8 Sonnet calls/case × ~3k tokens; a full 12-case sweep ≈ 60–100 small calls, ~25–40 min wall clock). To stay inside plan limits: use `haiku` for development iterations, run full Sonnet sweeps only at changelog checkpoints (v0–v3 + final), and space sweeps across usage windows. For a judge reproducing with a billed API key instead, one sweep ≈ $6–10 (token counts from the ledger get written into REPRODUCE.md so the estimate is evidence-backed).

## 10. Top 3 Risks & Mitigations

1. **Claim-to-gold alignment gets mushy (the judges' explicit hook).** Mitigation: spans, not similarity — gold claims are character spans emitted by the generator; systems must quote their span; primary alignment is deterministic span-IoU, fuzzy matching demoted to a flagged fallback with every fallback match published for inspection. Scorer has pytest fixtures with hand-labeled tricky paraphrases. Decision gate at H7: if span-quoting compliance <95% in early runs, add a one-line output-format retry (cheap) before ever touching the card format.
2. **Clean-clone friction (downloads + 1M-row file).** Mitigation: all six real datasets are small samples committed in-repo with licenses and checksums; the 1M-row hard case is *generated* deterministically by `make data` in under a minute; judge path requires zero network beyond the Anthropic API. Rehearsed from an actual fresh clone + venv at H34, with both PowerShell and bash commands documented.
3. **Agent loop burns the clock (SDK friction, flaky JSON, runaway retries).** Mitigation: orchestrator is deterministic Python — LLM calls are single-purpose with pydantic-validated outputs and a hard cap of 2 retries per step; if the Agent SDK client misbehaves on Windows, the identical pipeline runs on headless `claude -p --output-format json` subprocess calls, which use the same subscription auth (stages are already isolated functions, swap is ~1 hour). Scope fuse: if H21 arrives without v2 green, cut cases 10–11 (10 cases still meets the bar) rather than cutting the mutation loop — the mutation loop is the submission.
4. **(Added) Subscription usage limits instead of API billing.** All model calls draw from the Claude plan's rolling usage window shared with interactive Claude Code use. Mitigation: develop against 2–3 cases with `haiku`, reserve full Sonnet sweeps for the five changelog checkpoints, and schedule the two heaviest sweeps (H21–H23, H23–H26) right after a fresh usage window. If a wall is hit mid-sweep, the run ledger's skip-settled-claims cache means the sweep resumes where it stopped instead of restarting.

## 11. Candidate Hot Takes (validate while working)

1. **"LLM-written verifiers fail exactly like human-written ones: green does not mean tested. N% of first-draft checks passed vacuously until we mutation-tested the checks themselves."** Validation is built in: the v2 gate logs every check rejected by a mutant fixture; publish the rate, two concrete vacuous-check exhibits (e.g., a dtype-coerced comparison that could never fail), and the v1→v2 F1 delta.
2. **"More context made the baseline more confident, not more correct."** Validation: compare baseline vs baseline-plus per-claim — hypothesis is that `describe()` output *increases* confident 'holds' verdicts on claims describe() cannot actually settle (rare categories, row-position effects, cross-column rules), raising false-alarm-free confidence while violated-recall barely moves. If the data shows it, one scatter of confidence-vs-correctness per baseline tells the story; if it doesn't, fall back to the abstention lesson (the agent initially "verified" provenance prose it had no way to check — calibrated abstention was worth more F1 than any smarter check).
